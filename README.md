# app-rshlnk-data — канал подписанных документов «Решальника»

## Что тут лежит

- `update` и `update.sig` — **боевой узел**. Клиент читает ровно эти два пути.
  **Сейчас их НЕТ намеренно** (решение владельца 2026-08-01): активного
  документа не существует, пока не написана настоящая кампания.
  Клиент в этом состоянии получает отказ узла и живёт на своём seed —
  это штатное fail-closed поведение, а не поломка.
- `reference/update.reference.json` и `reference/update.reference.sig` —
  **образец**: валидный документ ревизии 1 и подпись к нему. Клиент их не
  читает; они существуют, чтобы следующая публикация копировала известную
  рабочую форму.

## Как публиковать (проверено на практике 2026-08-01)

1. Править документ, **обязательно** поднимая `revision` — клиент не примет
   ревизию меньше закэшированной.
2. Проверить схемой: `PromoDocument.model_validate_json()` из
   `server/promo/schemas.py` основного репозитория.
3. Подписывать **ровно те байты, которые отдаст узел**: нормализовать переводы
   строк в LF ДО подписи, иначе git закоммитит нормализованный файл и подпись
   не сойдётся.
4. Подпись публиковать **в base64** (клиент принимает и 64 сырых байта, и
   88 символов base64 — но сырые байты git на Windows калечит, превращая
   каждый `0x0A` внутри подписи в `0x0D 0x0A`).
5. Класть оба файла **одной операцией по смыслу** и лучше через GitHub
   Contents API, минуя рабочую копию.
6. Проверять СОДЕРЖИМОЕ РЕПОЗИТОРИЯ, а не свой файл:
   `gh api repos/a-ulianov/app-rshlnk-data/contents/update -H "Accept: application/vnd.github.raw"`.
7. Помнить про кэш CDN: `raw.githubusercontent.com` отдаёт `max-age=300`, то
   есть до пяти минут узел показывает прежние байты.

Приватный ключ подписи в этом репозитории отсутствует и никогда сюда не
попадает.
